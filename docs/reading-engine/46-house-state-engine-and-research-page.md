   it, each row carrying its provenance (`engine:<type>@<calc_version> <json path>`). The layers: natal promise,
   natal afflictions, activation by every dasha system, transits, the annual chart compounding the year, the
   divisional chart that owns the house's matter, and the nakshatra charter (§B).

7. **Phases:** 0 catalog truth and schema; 1 the deterministic engine on the five served layers with a golden test on

Two more "methods" sit beside the chart and are part of every verdict: the **ledger** (what actually happened, doc 27
§A.7) and the **person's own word** (doc 43 §8.1). Neither changes a chart value; both change confidence.

### A.2 The reading grammar (the same for every house)

1. **Promise** (natal): can the house give its matters at all, and in what style? Parashara and Jaimini, plus the
   nakshatra charter. A house with no promise gets no dates, only "not shown in your chart".
2. **Affliction** (natal): what is in the way, permanently or until a release. Parashara, doshas, avasthas.
3. **Activation** (period): is the house switched on now? Every dasha system, grouped into independent families, one
   planet one vote. Without activation, nothing happens however strong the promise.
4. **Trigger** (transit): what brings it to a date inside the activation. Gochara, double transit, Ashtakavarga bindus,
   eclipses, stations.
5. **Annual compounding** (Tajaka): does this year's chart confirm, amplify or contradict? The year never decides alone.
6. **Drill-down** (vargas): the divisional chart that owns the matter agrees or disagrees; D1 and the owning varga must
   agree for a dasha vote to count (doc 43 §8.1).
7. **Focus**: which sub-area of the house is the one being pressed or opened, read from the specific points activated
   (the 2nd from the 7th is a different story from the 12th from the 7th).

A verdict is stated only as strongly as the families agree; a split is shown as a split.

## Part B — The house-state engine

### B.1 The unit of work and its output

```
HouseState(kundli_id, house: 1..12, from: date, to: date, options)
→ {
  house, range, as_of,
  verdict: { side: supported|steady|tested, confidence: confirmed|likely|split, score: {support, test}, focus: sub_area_id },
  layers: {
    promise:     { score, charter: string, rows: Evidence[] },
    affliction:  { score, releases: [{planet, until, source}], rows: Evidence[] },
    activation:  { families: [{family, system, lord|sign, level, from, to, vote, validated_by: {D1, Dn, D9, D60}}], rows },
    transit:     { rows, double_transit: bool, sade_sati: phase|null, eclipses: [...] },
    annual:      { year, chart: tithi_pravesha|varsha, rows, compounds: confirms|amplifies|contradicts|silent },
    varga:       { chart: 'D10', rows, agrees: bool },
    nakshatra:   { cusp, lord_star, occupant_stars, deliverer, charter: string, rows }
  },
  subareas: [{ id, side, score, rows }],
  evidence: Evidence[]          // the union, deduplicated
}
Evidence = { layer, rule, value, weight, side, source: { type, variant, calc_version, engine_commit, path } }
```

Every number is a count or a sum over rows the engine returned. `path` is the JSON path inside that type's payload, so
the research page can show the raw value next to the rule that used it.

### B.2 Layer 1 — Natal promise of house h

| Rule (Parashara unless marked) | Engine field (type → path) | Weight |
|---|---|---|
| Lord of h in a kendra or trikona from lagna, or in h itself | `facts` → `houses[h].lord`, `.lord_house`; `house_counts.house_class` | +2 |
| Lord of h in 6, 8 or 12 from lagna, or 6/8/12 from h | same | −2 (and an affliction row) |
| Lord's dignity: exalted, own, moolatrikona / debilitated (neecha bhanga checked) | `dignities` → `planets[].dignity`; `yogas` → neecha-bhanga pairs | +2 / −2 |
| Benefic occupants (functional, for this lagna) / malefic occupants | `benefic_malefic` → `functional`; `facts.houses[h].occupants` | +1 each / −1 each |
| Graha drishti of a functional benefic / malefic on h | `aspects` → graha drishti on house h; `benefic_malefic` | +1 / −1 |
| Rasi drishti (Jaimini) of benefics / malefics on h | `aspects` → rasi drishti | +0.5 / −0.5 |
| Argala net on h: subha argala unobstructed / papa argala | `argala` → `houses[h].argalas`, `virodhargala` | +1 / −1 |
| SAV of h's sign ≥ 28 / ≤ 22 | `ashtakavarga` → `sav_by_house[h]` | +1 / −1 |
| Bhava bala rank of h in the top 4 / bottom 4 | `strength.bhava` → `houses[h].rank` | +1 / −1 |
| A yoga whose planets or houses include h or its lord (Raja, Dhana, Mahapurusha, named yogas) | `yogas` → `yogas[].houses`, `.planets`; `facts.yogas` (parivartana, Dhana pairs) | +1 to +3 by class |
| A dosha touching h (kalathra on 7, pitru on 9, manglik on 1/4/7/8/12 …) | `doshas` | −1 to −2 |
| Natural karaka of h strong / weak (Su 1 9 10; Mo 4; Ma 3 6; Me 4 10; Ju 2 5 9 10 11; Ve 7; Sa 6 8 10 12) | `strength.shadbala` → `planets[].ratio` | +1 / −1 |
| Arudha of h (A_h) with benefics / malefics, and its lord's state (Jaimini) | `arudhas` → `bhava_arudhas[h]`, occupants | +1 / −1 |
| The special lagna tied to h in a good sign and aspected by its lord (§B.9) | `facts.special_lagnas` | +1 |
| Lord of h in a good avastha (jagrat, deepta) / a dead one (mrita, sushupta) | `avasthas` → `planets[].jagradadi`, `.deeptadi`, `effective_delivery_multiplier` | ×1.25 / ×0.5 on the promise |

The promise score is the sum, capped to −8..+8; the **charter** sentence comes from the nakshatra layer (§B.8) plus the
strongest two rows here. A promise below −3 marks the house *not promised* for its primary matters; sub-areas may still
be promised through their own points.

| Combust / in war / debilitated lord | | `dignities.planets[].combust`, `.planetary_war_with`, `.dignity` | neecha bhanga pairs give a release; combustion gives none |

| Papakartari on h (malefics in h−1 and h+1) | | occupants of h±1 from `facts.houses` | none; weight only |
| Nodes on the axis of h (Ra/Ke in h or h+6) | | occupants | eclipse windows on the axis amplify (transit layer) |
| Dosha membership | kalathra, manglik, pitru, guru-chandala, ganda moola, ghata, shrapit, kala sarpa | `doshas` | exceptions returned by the engine (manglik cancellations) count |

Afflictions never flip a verdict by themselves; they set the **baseline** against which activation and transits are
read (doc 32 Part 1's idea, now coded here), and they name the **blocker** on a sub-area's focus card.

### B.4 Layer 3 — Activation now, by every dasha system

**Families** (independent clocks; one planet one vote across families 1, 2 and 4):

| # | Family | Systems (engine types) | How the vote for house h is cast |
|---|---|---|---|
| 1 | Main graha clock | Vimshottari L1–L3 (`dasha.vimsottari.l3`) | the running MD, AD and PD lords' polarity to h (table below); PD decides between AD and PD when they differ |
| 2 | Conditional graha clock | the systems `dasha.applicable` says apply, at L3 where served (Ashtottari, Dwisatpathi, Chathuraaseethi, Shodasottari…) | same polarity rule; no vote when none applies |
| 3 | Rasi clock | Narayana primary (`dasha.narayana`), Chara and Sudasa as confirmers; Drig, Shoola, Kalachakra, Moola as research-only extras | the running sign counted from h and from A_h: 1, 5, 9, 10, 11 from h support; 6, 8, 12 from h test; the sign's occupants and lord add their polarity |
| 4 | Karaka clock | `dasha.karaka.l3`, with Kaala and Naisargika as research extras | the running karaka's relation to h: the chara karaka that signifies h (AK 1, AmK 10, BK 3/11, MK 4, PiK 9, PK 5, GK 6, DK 7) running gives support unless afflicted in the owning varga |
| 5 | Annual clock | the year's tithi ashtottari (`annual.tithi_pravesha_dasha`), Mudda, Patyayini | the running year-lord's place in the year chart relative to h (§B.6) |
| 6 | Transit clock | the slow planets and eclipses (§B.5) | one vote per the transit layer |
| 7 | Short confirmers | Yogini and Tithi Ashtottari L3, counted together (`dasha.yogini.l3`, `dasha.tithi_ashtottari.l3`); Tithi Yogini, Yoga Vimshottari, Tara and Saptarishi as research-only extras | vote only when the two agree |

**Polarity of a running planet P to house h** (the same table drives every family):

| P supports h when | P tests h when |
|---|---|
| P lords h, or occupies h | P lords 6, 8 or 12 from lagna and is not also a lord of h |
| P is the natural or chara karaka of h | P occupies 6, 8 or 12 from h |
| P lords or occupies 5, 9, 11 from h (the house's own trines and gains) | P is the lord of 8 or 12 counted from h |
| P aspects h by graha drishti and is a functional benefic | P aspects h by graha drishti and is a functional malefic (Sa, Ma, Ra, Ke, and the lagna's malefics) |
| P is the dispositor of h's lord and is strong | P is debilitated, combust or in a dead avastha (any link turns adverse) |
| P sits with A_h or aspects it by rasi drishti (Jaimini) | P is the baadhaka lord of h's sign (`house.baadhakas_of_raasi`, needs serving) |

A dasha vote **counts only when D1 and the owning varga agree** on P's state (doc 43 §8.1); D9 breaks a tie; D60 confirms
only when the birth time is recorded to the minute. Weights follow doc 29 §3 (S1 3, S4 2, confirmers 1, conditional 1.5
when it applies) and are tuned only by the ledger (doc 29 §5).

### B.8 Layer 7 — The nakshatra charter of the house

A house spans 30°, nine padas, two and a quarter stars. Three stars carry the house's charter:

| Star | Field | What it tells |

### B.10 Scoring and the verdict

```
support = Σ weights of support rows across layers 3–6   (activation, transit, annual, varga)
test    = Σ weights of test rows across layers 3–6
baseline = promise score (layer 1) − affliction score (layer 2), scaled to ±2
side    = supported  when support − test + baseline ≥ +2
        = tested     when test − support − baseline ≥ +2
        = steady     otherwise
confidence = confirmed  when ≥ 5 of the 7 families (§B.4) vote the same side, including family 1 and 6, and family 1's
                          vote is validated by D1 and the owning varga
           = likely     when 4 of 7 agree with at most one of those conditions missing
           = split      otherwise
focus   = the sub-area (§B.11) with the highest |support − test| among those whose own points were touched
```

The thresholds are those of doc 43 §8.1 and are pinned until the ledger tunes them (doc 29 §5). Over a date range, the
engine returns the verdict per month (and per week when the daily sky is stored) so the research page can draw six
months ago, this year and now side by side. The consumer tones (doc 45 §7) are a rename of *side × trend*: tested →
Demanding, tested but ending within 30 days → Easing, steady → Steady, supported and ending within 30 days → Closing,
supported → Open.

### C.3 The provenance rule

Every value on the research page carries `engine:<type>@<calc_version> <path>` and the `engine_commit` of the run.
Node code in `src/reading/houseState/` may **select** a field, **count** rows, **intersect** date ranges and **sum**
weights. It may not derive a sign from a longitude, an aspect from positions, a yoga from placements, a house from a
sign, or a dignity. A unit test (`noAstrologyInNode.test.ts`) greps the module for the forbidden operations (sign
arithmetic on longitudes, hard-coded aspect tables, nakshatra boundaries) and fails on any hit. The *Check says* column
comes from the harness in the engine repo, never from Node.

## Part E — The research page

### E.1 Where it lives and who sees it

The staff admin app (`aiadastra_admin`, built 2026-11-04: Vite web app, its own API and Lambda, `admin_accounts` table)
gets a **Research** section. The engine API lives on the server Lambda, under `/api/research/*`, guarded by a role check
on the JWT (`researcher` or `aiastra_admin`; REST routes have no guard today, so doc admin/01's `requireRole` middleware is
the dependency) and by `RESEARCH_ENABLED=1`. The public web app is untouched.

### E.2 The page

**Inputs:** kundli (search by email or id, or the three research kundlis as presets), date range (defaults: six months
ago → today, and today → +12 months), granularity (month / week), house or board (all 12 by default), options (owning
varga override, include research-only dashas, birth-time quality).

**Output, top to bottom:**
1. **Run bar:** engine commit, calc versions, run time, "Run again", "Export JSON".
2. **Twelve house cards** in a 3×4 grid: house number and name, the verdict side and confidence, the focus sub-area, a
   small month strip over the range (side per month), and the family votes as seven dots.
3. **House detail** (tap a card): the accordion per method:
   - *Parashara*: promise rows, affliction rows, activation rows by family, gochara rows;
   - *Jaimini*: arudha, karaka, rasi drishti, argala, rasi clock rows;
   - *Tajaka*: the year chart's rows, sahams in houses, annual dashas, muntha and Tajaka yogas (once served);
   - *Nakshatra*: the three stars, the charter rows, the deliverer chain, the day's tara;
   - *Ashtakavarga*: SAV, BAV of the lord, transit bindus;
   - *Vargas*: the owning varga's rows and `agrees`;
   - *Sub-areas*: each with its five focus questions answered from rows.
   Every row: rule · value · weight · side · **Engine says** (`type@version path`) · **Check says** (from
   `house_state_checks`, with ✓ / ✗ / "not checked").
4. **Compare:** two date pickers ("six months ago" and "now" by default) show the same house side by side, with the rows
   that changed highlighted.
5. **Ledger overlay:** the person's life events inside the range drawn on the month strip, so a verdict can be eyeballed
   against what happened; a "mark hit / miss" button writes to `timeline_matches`.
6. **Raw payloads:** a drawer that shows the `kundli_data` payload of any type used in the run.

Technical names are allowed on this page (Sanskrit, planet names, D-chart ids). None of doc 45's consumer rules apply.
It is not localised. It renders at desktop width only.

### E.3 States

Pending (no run yet: "Run" button), running (stage line: data → windows → scoring; 30–90 s on stored rows; up to 4 min
when annual types must be pulled), ready, partial ("3 types not served: muntha, year lord, Tajaka yogas", listed, with
the rows that depend on them greyed), failed (the error and the type that failed).

### F.4 Backend flows

1. **Run** (`POST /api/research/house-state`): validate role and flag → create `house_state_runs` → stage *data*:
   `ensureChartData` for the layer types of §C.1 for the kundli (natal once; annual for the years in range; the shared
   sky and overlay for the range; missing types are pulled with the existing throttle, 4 concurrent with an API key, 120
   s timeout, 3 retries on 429/503 only) → stage *layers*: compute the seven layers per house per month from stored
   payloads (pure selection and counting; under 5 s for 12 houses × 24 months) → stage *score* (§B.10) → write
   `house_state_months` and `house_state_evidence` → status ready. A failed pull marks the run *partial* with the
   missing types listed; the layers that need them are skipped, never faked.
2. **Compare**: two runs or two months of one run; computed on read from stored rows.
3. **Checks**: the harness JSON is uploaded by a script (`npm run research:checks -- file.json`) into
   `house_state_checks`; the page joins by `(type, rule)`.
4. **Reuse by the boards (doc 45)**: the tone engine reads `house_state_months` for houses 1, 7 and 10 (plus their
   supporting houses) instead of its own vote code; one implementation of §B.10 serves both.

Limits: one run per kundli at a time (409 with the running id); a run is capped at 48 months; runs older than 30 days are
pruned by a nightly sweep (evidence rows only; verdict rows are kept for calibration).
